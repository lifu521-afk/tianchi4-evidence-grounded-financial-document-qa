## 2. 项目解决什么问题

### 2.1 业务问题

金融企业会积累大量：

- 年度报告、半年度报告和财务报表
- 债券募集说明书、发行文件和合同
- 保险产品条款、责任说明和免责条款
- 监管法规、公司章程和公告
- 行业研究报告、预测和风险提示

业务人员常见的问题不是“请聊天”，而是：

```text
这个数字在原文哪一页？
这个条款的触发条件是什么？
两份文档中的指标哪个更高？
这个选项是否真的被原文支持？
这个计算结果的原始数值和单位是什么？
模型的答案能不能被复核、审计和提交？
```

### 2.2 为什么普通 LLM 问答不够

直接把整份文档放入 Prompt 有几个风险：

1. **上下文过长**：成本高，模型注意力可能被无关内容分散。
2. **数字错配**：把不同年份、不同单位或不同公司的数字混在一起。
3. **条款错配**：命中了相似主题，却漏掉例外条件、适用对象或时间限制。
4. **多选题漏判**：只找到支持某个选项的证据，忽略其他选项的反证。
5. **幻觉**：原文没有说，模型却使用金融常识补全。
6. **过程不可审计**：只有一个答案，没有来源、调用记录和 Token 依据。
7. **运行不稳定**：网络错误或终端中断后，已经完成的题目被重复运行。

因此项目的核心目标是：

```text
答案 = 指定原文中的证据 + 题型约束下的判断 + 可校验的结构化输出
```

## 3. 全局技术架构

```text
原始文档和题目
PDF / HTML / TXT / JSON
        |
        v
预处理层
解析、清洗、表格保留、文档映射、页级信息
        |
        v
索引层
中文 n-gram、词项、数字、条款号、领域关键词
        |
        v
RAG 检索层
题干召回 + 选项召回 + 锚点召回 + 文档覆盖 + 邻近扩展
        |
        v
Agent Harness
任务生命周期、批量调度、Hook、重试、失败隔离、耗时
        |
        v
Agent Runtime
Planner -> Retriever Tool -> Solver -> Reflection -> Validator
        |                                             |
        v                                             v
Memory                                      Evidence Gate / Review
短期记忆、长期经验                           证据一致性和答案保护
        |
        v
输出层
answer.csv / evidence.json / reasoning / raw usage / summary
        |
        v
质量层
格式校验、证据覆盖、答案有效性、准确率、Token 和运行诊断
```

### 3.1 分层架构的意义

| 层 | 主要职责 | 失败时应该排查什么 |
| --- | --- | --- |
| 数据层 | 找到并读取原始文档和题目 | 文件路径、编码、格式、缺失文档 |
| 预处理层 | 转换成统一内部结构 | 页码、表格、切片、文档 ID |
| 检索层 | 找到候选证据 | 查询词、召回数量、领域配置 |
| 模型层 | 根据证据做判断 | Prompt、模型、输出解析 |
| 校验层 | 阻止非法或无证据结果 | 题型规则、Evidence Gate、字段检查 |
| 运行层 | 让长任务可靠执行 | 缓存、重试、停止、续跑、预算 |
| 评测层 | 衡量效果和成本 | Accuracy、覆盖率、Token、延迟 |

分层的好处是可以回答“错误到底来自哪里”。如果不分层，所有问题都会被模糊地归因于“大模型不够聪明”。

## 4. 文档处理知识点

### 4.1 文件格式和解析

项目支持 PDF、HTML、TXT 等来源。

| 技术 | 通俗解释 | 项目用途 |
| --- | --- | --- |
| PDF parsing | 从 PDF 页面中抽取文字和表格 | 财报、合同、募集说明书 |
| HTML parsing | 去掉标签，保留可见文本 | 网页型公告或研究材料 |
| TXT encoding fallback | 尝试多种编码读取文本 | 处理不同来源的中文文件 |
| page metadata | 给文本附加页码 | 让证据可以回溯 |
| table extraction | 把表格行转换成可检索文字 | 保留财务指标和比例 |

PDF 不是天然的“文字文件”。常见情况包括：

- 文字层存在，但阅读顺序错乱
- 表格被拆成多个文本块
- 页眉页脚重复出现
- 扫描 PDF 只有图片，没有文字层
- 数字和单位被分离

所以工程上不能只调用一个 `extract_text()` 就认为解析完成。项目通过页级抽取、表格保留、重复边缘文本处理和预处理报告降低这些问题。

### 4.2 文本清洗

文本清洗的目标不是把文字“变漂亮”，而是让检索稳定：

- 统一空白和换行
- 去掉无意义的重复页眉页脚
- 保留数字、百分号、条款编号和单位
- 不随便删除否定词“不得”“不超过”“未发生”
- 保留表头和必要上下文

金融文本中，过度清洗可能直接改变语义。例如：

```text
不超过 70%
超过 70%
```

如果清洗时丢掉“不”，检索和答案都会反转。

### 4.3 Chunk 切片

长文档需要切成多个 Chunk 才能建立索引。一个 Chunk 通常保存：

```text
chunk_id
doc_id
domain
title
source_path
page
page_char_start
page_char_end
block_type
text
```

关键概念：

- **Chunk size**：每片文本大小。太小会丢上下文，太大增加 Token。
- **Overlap**：相邻片段重叠区域。用于避免一句话被切断。
- **Source span**：原文字符位置，支持回溯和人工审计。
- **Block type**：区分普通文本、表格或混合片段。

切片不是越小越好。金融条款经常有“主句 + 限定条件 + 例外条件”，必须通过合理切片和邻近扩展保留完整语义。

### 4.4 数据契约

预处理后的数据应该有稳定结构，而不是让后续模块猜字段。项目中的题目结构通常包含：

```python
{
    "qid": "question-id",
    "domain": "financial_reports",
    "question": "题目文本",
    "options": {"A": "选项文本", "B": "选项文本"},
    "answer_format": "mcq",
    "type": "单选题",
    "doc_ids": ["source-document-id"]
}
```

这对应软件工程中的 **Data Contract**：上下游模块约定字段、类型和含义，减少隐式假设。

## 5. RAG 与检索知识点

### 5.1 RAG 是什么

RAG 是 Retrieval-Augmented Generation，即“检索增强生成”：

```text
先从知识库找证据，再把证据交给模型生成答案
```

它把“知识定位”和“语言生成”拆开：

- Retriever 负责找材料
- LLM 负责理解材料、推导和表达
- Validator 负责检查答案是否真的被材料支持

RAG 的关键不是“接入一个向量库”，而是证据是否真的覆盖问题和选项。

### 5.2 Lexical Retrieval 与 BM25

项目核心使用轻量词法检索，借鉴 BM25 思路。

BM25 的直观思想：

1. 查询词在文档中出现，文档得分增加。
2. 一个词在很多文档中都出现，区分度低，权重下降。
3. 一个词在少数文档中出现，区分度高，权重上升。
4. 文档过长不能无限获得优势，要做长度归一化。

简化后的 BM25 相关概念：

```text
TF  = 词在当前文本中出现的频率
IDF = 词的区分度
Length normalization = 文本长度归一化
```

项目将中文字符、二元片段、英文词项、数字和结构化词项组合起来，适合金融文档中的精确匹配。

### 5.3 为什么金融场景适合词法检索

金融题目经常要求精确识别：

```text
2024 年
70%
150%
每 10 股
第八十二条
5 个工作日
票面利率
资产负债率
```

词法检索的优势：

- 对数字、年份、单位和条款号可解释
- 本地运行，不需要额外 embedding API
- 召回结果容易展示给人工审核
- 索引构建快，适合反复实验

局限：同义改写和深层语义关系可能召回不足。因此后续可扩展：

```text
BM25 / lexical retrieval
        +
Embedding retrieval
        +
Cross-encoder reranker
```

但是否能使用外部 embedding、外部模型和第三方服务，必须遵守比赛或企业数据规则。

### 5.4 四类召回

#### 题干级召回

根据问题主题召回整体相关片段。例如“研发投入占营业收入比例”会优先查找研发投入、营业收入、比例等词。

#### 选项级召回

对每个选项独立检索。多选题必须逐项查证，因为题干证据相关不代表每个选项都正确。

#### 结构化锚点召回

识别以下高价值内容：

- 金额和百分比
- 日期和期限
- “第 X 条”
- “应当”“不得”“可以”“必须”
- 评级、利率、回售、赎回和担保
- 财务指标名称

#### 邻近上下文扩展

把命中 Chunk 前后的片段加入证据，恢复表头、标题、脚注和条件限制。

### 5.5 召回和排序的区别

- **Recall / 召回**：相关证据有没有进入候选集合。
- **Ranking / 排序**：相关证据在候选集合中的位置是否靠前。
- **Reranking / 重排**：使用更强模型对候选结果重新打分。

一个系统可能召回了正确片段，但它排得太靠后，最终没有进入 Prompt；这属于排序问题，不一定是召回问题。

### 5.6 检索指标

有人工标注证据时，可以计算：

```text
Recall@K = 前 K 个结果中包含相关证据的问题数 / 总问题数
MRR      = 第一个正确证据排名的倒数平均值
Precision@K = 前 K 个结果中相关证据的比例
```

企业项目还应按领域、题型、文档类型和跨文档问题分别统计，不能只看一个总平均数。

## 6. 金融领域知识点

### 6.1 财务报告

重点核对：

- 报告年份和期间
- 合并口径或单体口径
- 元、万元、亿元等单位
- 营业收入和营业总收入
- 归母净利润和净利润
- 经营活动现金流
- 研发投入、研发费用和占比
- 分红、回购和每股指标
- 同比增长、同比下降和比较基准

典型错误：把“增长率”当成“增长金额”，把“归母净利润”当成“净利润”，或者把 2023 年数据和 2024 年表头错配。

### 6.2 金融合同和债券文件

重点核对：

- 发行人和发行主体
- 发行规模、期限和起息日
- 票面利率、付息日和兑付日
- 信用评级和评级展望
- 担保、增信和无担保表述
- 回售、赎回和触发条件
- 募集资金用途
- 违约责任、违约金和逾期利息

合同题不能只匹配“回售”这个词，还要检查谁可以回售、什么时候可以回售、回售价格和通知方式。

### 6.3 保险条款

重点核对：

- 保险责任触发条件
- 被保险人年龄和保险期间
- 等待期、犹豫期和冷静期
- 身故保险金和给付比例
- 现金价值、账户价值和已交保费
- 退保、领取和合同终止
- 免责条款和不赔付情形

保险条款中“可以领取”“应当给付”“不承担责任”不是同一强度的表达，必须保留原文的义务和限制关系。

### 6.4 监管文件和公司章程

重点核对：

- 条款编号
- 应当、不得、可以、必须
- 普通决议和特别决议
- 过半数、三分之二以上
- 股东会和股东大会权限
- 对外担保触发条件
- 变更募集资金用途
- 独立董事资格与利害关系
- 报告、备案和工作日限制

不能使用“法律常识”代替指定原文。一个选项只要多出一个原文没有的绝对化条件，也可能是错误项。

### 6.5 研究报告

重点核对：

- 行业规模和市场份额
- 增速、CAGR 和预测年份
- 公司比较指标
- 毛利率、净利率和 ROE
- 投资评级和目标价
- 研究结论和风险提示

研究报告中的“预测”“预计”“有望”不能被改写成确定事实；“建议关注”也不等于“买入”。

## 7. Agent 知识点

### 7.1 Agent 和普通 LLM 调用的区别

普通调用通常是：

```text
Prompt -> LLM -> Text
```

Agent 系统还要处理：

```text
目标、计划、状态、工具、记忆、判断、反思、失败和下一步动作
```

因此 Agent 不是“给模型加一个更长的 Prompt”，而是一个具有运行状态和执行闭环的软件系统。

### 7.2 Planning

Planning 是把复杂任务拆成可执行步骤。项目中的计划类似：

```text
retrieve_evidence
validate_evidence
solve
reflect
validate_output
commit_memory
```

计划的价值：

- 每个步骤职责明确
- 可以记录状态和失败位置
- 可以替换某一个 Agent，而不重写全部流程
- 可以针对题型增加步骤，例如计算题增加 calculate

### 7.3 State

AgentState 是工作流的共享状态，包含：

```text
task_id
question
plan
current_step
evidence
candidate_answer
final_answer
reasoning
reflection
memory_hits
tool_calls
usage
trace
errors
status
```

状态对象解决了“每个函数都靠隐式全局变量传数据”的问题，也使运行结果可以序列化、恢复和审计。

### 7.4 Tool Use

Tool Use 是 Agent 调用外部能力。项目用 `ToolRegistry` 管理工具：

- 工具名称
- 工具描述
- 处理函数
- 必填参数
- 调用参数和耗时

为什么要注册表，而不是随便执行函数？

1. 只有白名单工具可以被调用。
2. 参数不完整时可以提前失败。
3. 可以统一记录工具调用。
4. 未来接入数据库、搜索、计算或人工审核时接口一致。

### 7.5 Multi-Agent

项目中的多 Agent 更准确地说是“多角色协作工作流”：

```text
Planner Agent       负责任务拆解
Retriever Agent     负责找证据
Solver Agent        负责基于证据作答
Reflection Agent    负责结果检查
Validator           负责结构化输出校验
```

多 Agent 不一定意味着多个模型实例。它可以是同一个 Qwen 模型在不同角色 Prompt 下工作，也可以在以后路由给不同模型。

### 7.6 Reflection

Reflection 是对结果进行二次检查，不等于让模型无限思考。项目当前的 Reflection 主要检查：

- 答案是否为空
- 是否符合单选、多选或判断题格式
- 是否有证据
- 是否需要规范化
- reasoning 是否过短

更复杂的 Reflection 可以检查：

- 每个选项是否都有证据
- reasoning 是否真的引用了证据
- 计算结果是否重新计算一致
- 跨文档答案是否覆盖全部文档
- 新答案是否有足够证据推翻基线

### 7.7 Evidence Gate

Evidence Gate 是本项目的重要安全思想：

```text
模型提出的新答案
        |
        v
是否有直接支持新答案的证据？
或是否有直接反驳旧答案的证据？
        |
   是 -> 允许进入候选结果
   否 -> 保留基线或进入人工复核
```

它解决了一个常见问题：模型复核并不总是比原答案可靠，重新调用模型可能把正确答案改错。

### 7.8 Agent Harness

Harness 负责“让 Agent 稳定地运行”，而不是负责业务判断：

- 统一单任务和批量任务入口
- 控制最大尝试次数
- 捕获异常
- 失败重试
- `before_task` 和 `after_task` Hook
- `fail_fast` 批量策略
- 统计耗时
- 合并所有重试的 Token 和轨迹

可以用一句话区分：

```text
Runtime 决定 Agent 如何完成任务。
Harness 决定任务如何可靠运行。
```

这与企业里的任务调度器、工作流引擎和服务治理比较接近。

### 7.9 State Graph

项目提供轻量 `StateGraph`：每个节点接收 AgentState，返回下一个节点名称或结束。

它包含的工程保护：

- 起始节点必须存在
- 未知节点失败关闭
- 检测循环
- 限制最大步骤数

它不是完整 LangGraph 的替代品，而是一个小型、无额外依赖的状态图抽象。项目另有可选 LangGraph adapter，只有安装 LangGraph 后才启用。

## 8. Memory 知识点

### 8.1 短期记忆

短期记忆保存当前任务或当前运行中的上下文，例如：

- 已经找到的证据
- 当前题目的判断
- 当前任务中的错误
- 前一步的工具结果

短期记忆应该有任务边界，不能让一个问题的内容无意间污染另一个问题。

### 8.2 长期记忆

项目的 `JsonlMemory` 可以保存经过审核的经验：

```json
{
  "domain": "financial_contracts",
  "question": "债券回售条款",
  "lesson": "核对回售触发条件、日期和价格",
  "answer": "A"
}
```

长期记忆适合保存“可复用经验”，不应该盲目保存所有模型输出。企业使用时还需要：

- 权限隔离
- 租户隔离
- 脱敏
- 版本管理
- 删除策略
- 记忆质量审核

### 8.3 Memory 检索

项目使用轻量词法匹配找到相似经验。未来可以扩展向量记忆，但必须控制：

- 记忆是否真的与当前问题相关
- 旧经验是否过期
- 记忆是否会造成错误偏置
- 不同客户的数据是否会串线

## 9. Prompt Engineering 知识点

### 9.1 金融问答 Prompt 的核心结构

一个可靠 Prompt 通常包含：

```text
角色：你是证据约束型金融文档问答 Agent。
任务：根据题目和给定证据确定答案。
边界：只能使用给定证据，不使用外部常识补全。
步骤：识别题型 -> 逐项判断 -> 核对数字/单位/限定 -> 得出结论。
输出：结构化 JSON，包含 answer 和公开 reasoning 摘要。
约束：答案必须符合题型，reasoning 必须与答案一致。
```

### 9.2 多选题为什么要求逐项判断

错误做法：

```text
请直接选择所有正确选项。
```

更可靠的做法：

```text
对 A、B、C、D 分别判断：supported / contradicted / insufficient。
为每个判断绑定证据 ID，再根据题型规则生成最终答案。
```

这样可以减少“看起来整体正确，但其中一个选项没有依据”的问题。

### 9.3 reasoning 不是隐藏思维链

提交的 reasoning 应该是可审计的公开摘要，而不是暴露隐藏思维链。推荐结构：

```text
证据位置：文档 ID、页码、条款或表格
关键事实：原文中的数字、条件或结论
判断过程：比较、排除或计算的必要步骤
结论：与 answer 完全一致
```

空泛的“根据文档可知，答案是 A”信息量太低，也无法支持审计。

### 9.4 结构化输出

让模型返回 JSON 的好处：

- 代码更容易解析
- 字段更稳定
- 可执行格式校验
- 答案和 reasoning 可以分别处理
- 便于保存和重试

但不能只相信模型返回 JSON。还需要代码做二次校验，因为模型可能返回：

- 多余 Markdown 代码块
- 非法选项字母
- 缺字段
- JSON 嵌套结构变化
- reasoning 和 answer 矛盾

## 10. 答案校验知识点

### 10.1 规范化

题型不同，答案处理规则不同：

| 题型 | 处理方式 |
| --- | --- |
| 单选题 | 取第一个合法字母 |
| 判断题 | 使用题目允许的判断编码 |
| 多选题 | 去重、按规定排序、完全匹配 |
| 计算题 | 保留数值、单位和格式要求 |
| 抽取题 | 按原文顺序填入答案槽位 |

规范化解决“模型输出了 `答案是 A。`”这类表面格式问题，但规范化不能修复语义错误。

### 10.2 证据支持检查

选项支持至少要检查：

1. 被引用的 evidence ID 是否存在。
2. evidence 是否来自允许的文档。
3. evidence 是否包含选项中的数字和单位。
4. evidence 是否支持同一个指标，而不是相似指标。
5. 是否存在否定词或例外条件导致语义相反。

### 10.3 计算题

计算题要保留：

```text
原始数值 -> 公式 -> 中间结果 -> 单位换算 -> 四舍五入 -> 最终答案
```

只输出一个数字而没有原始数值和公式，会降低可审计性。计算最好使用确定性 Python 工具二次计算，而不是完全依赖模型心算。

## 11. Token 与成本治理知识点

### 11.1 Token 是什么

Token 是模型处理文本时使用的基本计量单位，不等于字符数，也不等于中文汉字数。不同模型和 API 的 tokenizer 可能不同，所以合规场景必须使用 API 返回的原始 usage。

### 11.2 三个重要字段

```text
prompt_tokens     输入 Token
completion_tokens 输出 Token
total_tokens      API 返回的总 Token
```

如果同一道题有多次模型调用：

```text
题目总 Token = 初始调用 + 复核调用 + 摘要调用 + 重试调用 + 其他相关调用
```

不能只记录最后一次调用，也不能手工修改 Token 数值。

### 11.3 成本优化方法

项目支持多种上下文模式：

```text
full     更多证据，适合复杂高风险题
compact  平衡准确率和成本
minimal  较少证据，适合普通题
micro    更短上下文，适合低成本探查
nano     极短上下文，适合受控调试
```

合理的成本路由：

```text
低风险题 -> compact 或 minimal
数字/法规/多选高风险题 -> 更强证据覆盖
检索不足 -> 先修检索，不要盲目加长 Prompt
答案已有可靠证据 -> 避免重复复核
```

### 11.4 Token 与质量的权衡

Token 越多不等于准确率越高。过多无关证据会造成：

- 关键信息被淹没
- 模型把相似片段混淆
- 成本和延迟上升
- 复核调用带来答案回归

真正应该优化的是“单位 Token 带来的有效证据密度”。

### 11.5 Budget 控制

`CostLedger` 维护累计 usage 和任务预算：

```text
调用模型 -> 读取原始 usage -> 加入 ledger -> 检查预算 -> 决定是否继续
```

企业系统中还应增加：

- 单用户预算
- 单租户预算
- 每日预算
- 并发限制
- 超预算告警
- 供应商价格换算

## 12. 可靠性与工程化知识点

### 12.1 Checkpoint

Checkpoint 是中间进度保存点。长任务中每完成一道题就保存结果，避免程序中断后全部重跑。

### 12.2 Cache

单题缓存可以避免重复请求模型。缓存必须考虑：

- qid
- Prompt 版本
- 模型名
- 检索配置
- 文档或数据版本
- 是否包含完整原始 usage

如果 Prompt 或文档版本改变，旧缓存可能不能直接复用。

### 12.3 安全停止与续跑

项目支持：

```powershell
python train.py --mode stop
python train.py --mode resume
```

安全停止的关键是：

1. 当前题目尽量完成或保存失败状态。
2. 已完成题目写入 checkpoint。
3. 未完成题目不伪造结果。
4. 后续从缓存和 checkpoint 恢复。

### 12.4 重试和幂等性

网络错误、限流和服务端错误可以重试，但重试会产生额外 Token。工程上要：

- 设置最大重试次数
- 使用指数退避
- 区分可重试和不可重试错误
- 记录每次尝试
- 合并每次原始 usage
- 设计幂等缓存，防止重复写结果

### 12.5 失败隔离

批量任务中，一道题失败不应该让所有题丢失。Harness 的 `fail_fast` 可以按业务选择：

- 研究实验：失败后继续，收集更多样本
- 关键批处理：遇到失败立即停止
- 提交任务：失败应阻断最终文件，避免生成不完整结果

## 13. OpenAI-compatible API 知识点

项目使用兼容 `/chat/completions` 的接口，因此可以支持 DashScope 和符合协议的中转服务。

典型请求结构：

```json
{
  "model": "qwen3.6-plus",
  "messages": [
    {"role": "system", "content": "..."},
    {"role": "user", "content": "..."}
  ],
  "temperature": 0,
  "stream": false
}
```

重要 API 工程知识：

- `Authorization: Bearer <API_KEY>`
- `Content-Type: application/json`
- 超时控制
- HTTP 401：Key 或 endpoint 不匹配
- HTTP 404：路径重复或 Base URL 错误
- HTTP 429：限流，需要退避
- 5xx：服务端暂时错误，可有限重试
- `usage`：必须保留原始输入/输出/总 Token

配置优先级通常是：

```text
命令行参数 > local_config.py > 环境变量 > 默认值
```

API Key 只能放在本地配置或环境变量中，不能写入 GitHub。

## 14. 输出与评测知识点

### 14.1 结构化输出

项目会产生：

```text
answer.csv       最终提交答案
evidence.json    证据和审计信息
checkpoint       中间进度
cache            单题缓存
trace.json       Agent 运行轨迹
```

其中运行结果和数据集属于本地私有材料，不应上传公开仓库。

### 14.2 CSV 是接口契约

CSV 不只是导出文件，它是评测系统读取结果的接口。需要检查：

- 表头完全匹配
- qid 不重复、不缺失
- 题目数量正确
- 答案字段可解析
- reasoning 满足规则
- Token 字段是非负数字
- `total_tokens = prompt_tokens + completion_tokens`
- summary 与普通题目行求和一致

### 14.3 评测指标

项目离线评估可以统计：

| 指标 | 含义 |
| --- | --- |
| Accuracy | 有标准答案时，答案完全正确的比例 |
| Evidence coverage | 有至少一条证据的问题比例 |
| Answer validity | 有合法非空答案的问题比例 |
| Review rate | 被 Reflection 标记为需要关注的问题比例 |
| Average tokens | 每个任务平均 Token |
| Total tokens | 整批任务总 Token |
| Latency | 任务耗时，当前可从 Harness 轨迹统计 |

企业环境还需要：

- Unsupported answer rate：无证据回答率
- Abstention accuracy：证据不足时拒答是否正确
- Human acceptance rate：人工审核通过率
- SLA success rate：是否满足响应时间目标
- Cost per task：每任务成本

### 14.4 比赛分数和企业指标的区别

排行榜分数适合比较固定数据集上的提交结果；企业系统更关注：

```text
准确率 + 证据覆盖 + 可解释性 + 延迟 + 成本 + 数据安全 + 人工审核效率
```

不能只用一次比赛分数证明系统适合生产。

## 17. 推荐的讲解顺序

给别人介绍时可以按照下面顺序，逻辑最清楚：

### 第一步：先讲业务问题

“金融文档很长，答案必须来自指定原文，尤其容易错在数字、条款、年份、单位和多选题。”

### 第二步：讲为什么需要 RAG

“我不把整份文档直接交给模型，而是先解析和切片，再通过题干级、选项级和数字锚点检索证据。”

### 第三步：讲 Agent 工作流

“任务被拆成 Planner、Retriever、Solver、Reflection 和 Validator，每一步都有状态和轨迹。”

### 第四步：讲证据门控

“模型的新答案必须有直接证据，或者能直接反驳旧答案，否则保留基线或进入复核。”

### 第五步：讲 Harness

“Harness 解决的是运行稳定性，包括重试、批量执行、Hook、失败隔离、耗时和完整 Token 统计。”

### 第六步：讲企业价值

“结果不仅有答案，还有来源、reasoning、Token、状态和错误记录，可以复核、恢复和评估。”

## 18. 常见面试问题与回答思路

### Q1：为什么不用向量检索？

当前项目优先使用词法检索，因为金融题目高度依赖数字、年份、单位、条款号和专有名词，词法匹配可解释、成本低、便于审计。它不是否定向量检索，而是保留了后续扩展为混合检索和重排的接口。

### Q2：BM25 和向量检索有什么区别？

BM25 主要比较词项匹配和词项区分度；向量检索比较语义向量相似度。BM25 对精确数字和术语更直接，向量检索对同义改写更有优势。金融场景通常可以组合使用。

### Q3：如何降低幻觉？

先限制证据来源，再要求选项级判断，并对答案做 Evidence Gate 和结构化校验。模型只能降低风险，最终还需要人工抽检、黄金集和拒答策略。

### Q4：为什么需要多个 Agent？

不同角色有不同职责：检索负责找证据，Solver 负责判断，Reflection 负责检查，Validator 负责格式。拆分后更容易测试、替换和定位问题。多 Agent 不代表一定要使用多个不同模型。

### Q5：如何保证 Token 统计真实？

每次 API 调用都读取原始 usage，并按题目累计 prompt、completion 和 total。重试、复核和摘要调用也必须计入；缺少原始 usage 时，合规提交应失败关闭，不能手工估算替代。

### Q6：模型把正确答案改错怎么办？

不能让复核输出直接覆盖基线。通过 Evidence Gate 要求新答案有直接支持或旧答案有直接反驳；没有足够证据就保留基线或标记人工复核。

### Q7：Agent Runtime 和 Harness 的区别是什么？

Runtime 负责业务工作流和状态转移，Harness 负责执行治理。前者决定“做什么和怎么判断”，后者决定“如何稳定、可重试、可恢复地执行”。

### Q8：这个项目能直接用于生产吗？

目前更准确的定位是企业文档智能原型。生产化还需要权限继承、多租户隔离、PII 脱敏、加密、OCR、监控、任务队列、限流、人工审核和授权黄金集评测。

## 21. 最终总结

本项目最值得提炼的不是某一个模型名，而是一套完整的 LLM 应用工程思路：

```text
把非结构化金融文档变成可检索数据；
把检索结果变成可引用证据；
把问答过程拆成可观察的 Agent 工作流；
把模型输出变成经过规则保护的结构化结果；
把一次性脚本变成可恢复、可评测、可治理的系统。
```

适合在简历中突出三条主线：

1. **AI 能力**：证据增强 RAG、Prompt Engineering、Qwen、Multi-Agent。
2. **工程能力**：状态图、Harness、工具注册、缓存、重试、Checkpoint、CI。
3. **业务能力**：金融文档解析、数字和条款核验、证据审计、Token 和提交治理。
